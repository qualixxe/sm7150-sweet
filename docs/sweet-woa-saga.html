Sweet · Windows on ARM · Manual da Saga

A anatomia da saga do touch.

Um mapa do port de Windows 11 ARM64 no Redmi Note 10 Pro (sweet / sm7150): o que já funciona, onde cada periférico esbarra, a parede comum por trás de tudo — e o plano para acender o touch. Documento vivo; atualizar conforme avança.

Device: Xiaomi Redmi Note 10 Pro "sweet" SoC: sm7150 / Snapdragon 732G UEFI: edk2-sweet (dopaemon) Base: investigação jun/2026
🔥 Descoberta crítica — NÃO ESQUECER caminho do dual boot

O celular TEM uma partição dedicada de variáveis UEFI, achada via ls /dev/block/by-name/:

uefivarstore -> /dev/block/sde18

O UEFI do Aloha hoje usa variáveis RAM-only (PcdEmuVariableNvModeEnable=TRUE) e IGNORA essa partição. Por isso o BootOrder do Windows é apagado a cada reboot — e foi preciso o hack \EFI\Boot\bootaa64.efi pra conseguir bootar.

Fix definitivo: apontar o variable store do Aloha pra uefivarstore (sde18) como NV storage de verdade. Resultado:

  • Variáveis persistem → BootOrder sobrevive → dispensa o bootaa64.efi
  • Dual boot de verdade — várias entradas de boot que não somem no reset
  • Mata a raiz de vários asserts do Project Mu (variable policy, MemoryTypeInfo) que dependiam de variável real

⚠️ PRÓXIMO ALVO assim que o Windows bootar pela primeira vez. Alvo: /dev/block/sde18 (uefivarstore) → backend de variáveis do Aloha.

01 — Panorama

Onde estamos: boota, mas sem input.

O Windows 11 ARM64 sobe estável até o OOBE no sweet — sem loop de crash, sem watchdog. A maioria dos ports nem chega aqui. O que falta é a última milha: nenhum input funciona (touch, USB/OTG, WiFi, botões), e todos esbarram na mesma parede — a camada de energia/periférico (PMIC).

USB/OTG bloqueadodwc3 host mortoTestado powered + hardware bom. Falta o Type-C controller (PMIC).

A virada — o que descobrimos

O deploy atual é o mínimo (inject_min.bat = só qcgpio + qci2c + touch). O set completo (moorea, 82 INFs) tem PMIC, SPMI, Type-C, WLAN, botões — tudo que falta. A "parede do PMIC" é, na raiz, o driver do PMIC não estar deployado. O bloqueio exato para deployá-lo: o driver qcspmi pendura o boot.

02 — Arquitetura

A cadeia: do silício ao toque.

Para um dedo virar evento no Windows, a corrente atravessa estas camadas. O elo que falta é a energia (AVDD), e ela depende do PMIC — gerido por drivers que ainda não subiram.

Migração de IDs no DSDT (04xx → 14xx)

Para os drivers do moorea bindar, o DSDT precisa migrar os _HID ACPI: GIO0 140D ✓ · SPMI 140C · PMIC 142E · botões 1430 · IC10 1411 ✓. Hoje PMIC/SPMI/botões estão revertidos para 04xx (não bindam) justamente porque o qcspmi pendurava o boot.

03 — Barreiras

As paredes — e a parede comum.

Cada periférico morto é um sintoma. A doença é uma só: a camada de energia (PMIC) não está de pé no Windows.

B-01qcspmi pendura o boot (a raiz)crítico
SintomaMigrar o DSDT p/ 14xx (drivers PMIC/SPMI bindam) → o qcspmi (SPMI, boot-start) pendura o boot; o PMIC não enumera. Por isso foi revertido p/ 04xx.
EvidênciaDSDT.dsl: QCOM042E (PMIC, l.122), QCOM040C (SPMI, l.94262), QCOM0430 (botões, l.172) — todos com comentário "REVERTIDO… qcspmi pendurava o boot".
Causa provávelO hardware SPMI/PMIC não está inicializado (o backend que o UEFI stripped removeu) → o qcspmi pendura tentando acessá-lo.
DestravaVer ao vivo (serial/KDCOM) onde o qcspmi pendura → fazer só aquela init de SPMI no UEFI (sem o backend inteiro que crasha).
B-02Touch sem AVDD → 0x101crítico
SintomaTouch ativado → CLOCK_WATCHDOG_TIMEOUT (0x101). IC mudo no I2C; a IRQ de nível não é limpa → storm.
ProvadoNo UEFI: controlador I2C 100% pronto (FW=0x303, clocks on), bus elétrico perfeito após VDDIO+mux+pull-up, scan 0x08–0x77 = 0 devices → IC mudo → falta AVDD (LDO11_C).
Por quêSem driver de PMIC (B-01), o qcpep vota a AVDD mas não há quem ligue a LDO11. Subproduto de B-01.
B-03USB/OTG host mortoconfirmado
SintomaMouse via OTG não responde — testado adaptador normal E powered, hardware comprovadamente bom.
Registrorole-switch QCOM0497 enumerado, Service=UrsSynopsys, ConfigFlags=0 (habilitado). Não é driver faltando.
Por quêFalta o qcpmictcc (Type-C controller, no PMIC) → sem detecção de role → o dwc3 não vira host. Subproduto de B-01.
B-04WiFi sem driver · botões sem driverconfirmado
WiFiSó framework inbox (WifiCx/nwifi). Sem qcwlan7150. Único "adaptador" = KDNIC virtual. → WiFi+RDP fora (por ora).
BotõesSem qcpmicgpio7150 (está no full set, depende do qcspmi).
ComumAmbos = drivers do full set não deployados / dependentes do PMIC. Mesma raiz.
Um nó, não quatro

Touch, USB, WiFi e botões parecem 4 problemas — mas são um: o PMIC/SPMI não está de pé no Windows. Resolver o qcspmi (B-01) destrava o PMIC → e com ele a AVDD (touch), o Type-C (OTG), o qcwlan (WiFi) e os botões, de uma vez.

05 — Comandos

A bancada — como fazer cada coisa.

Folha de cola dos comandos que usamos. adb = D:\sweet\platform-tools\adb.exe. Cel em recovery pro acesso offline ao bloco.

Subir as ntfstools pro /tmp do cel

$adb   = "D:\sweet\platform-tools\adb.exe"
$src   = "E:\sweet_drivers\ntfstools"
$tools = 'mkntfs','wimlib-imagex','ntfscp','ntfscat','ntfsfix','ntfsls','ntfsinfo'
foreach ($t in $tools) { & $adb push (Join-Path $src $t) "/tmp/$t" }
& $adb shell "chmod 755 /tmp/ntfs* /tmp/mkntfs /tmp/wimlib-imagex"

Montar a MainOS (ntfs) no cel

# sda35 = MainOS (Windows). Acesso DIRETO no bloco c/ ntfsXXX (sem mount).
mkdir -p /mnt/win
mount -t ntfs /dev/block/by-name/Windows /mnt/win   # se o kernel tiver ntfs

Limpar estado sujo da NTFS

/tmp/ntfsfix /dev/block/sda35
/tmp/ntfsfix -d /dev/block/sda35   # -d = limpa o dirty bit

Trocar um arquivo do Windows (ex.: o driver do touch)

& $adb push E:\cel\cel\drivers\gtx9886-driver\driver\kmdf\ARM64\Release\vhidmini\vhidmini.sys /tmp
/tmp/ntfscp /dev/block/sda35 /tmp/vhidmini.sys /Windows/System32/drivers/vhidmini.sys

Ler logs do Windows offline

grep -ai "GDGT9889" /mnt/win/Windows/INF/setupapi.dev.log
grep -ai "vhidmini" /mnt/win/Windows/INF/setupapi.dev.log
# Hive sujo (reg do Windows) — hivexsh ignora o "dirty":
hivexsh /mnt/e/cel/SYSTEM   # cd \ControlSet001\Enum\ACPI\<HID>\<inst> ; ls ; lsval

Rebuild do UEFI (DSDT + imagem)

cd ~/sweet/uefi/edk2-sweet/F11/AcpiTables && iasl DSDT.dsl   # DSDT.dsl → DSDT.aml (0 errors)
cd ~/sweet/uefi/edk2-sweet && ./sweetbuild.sh                # gera sweet_uefi.img → flash

Injetar drivers numa WIM (DISM)

dism /Mount-Wim /WimFile:F:\install.wim /Index:1 /MountDir:C:\wmount
dism /Image:C:\wmount /Add-Driver /Driver:E:\sweet_drivers\moorea /Recurse /ForceUnsigned
dism /Unmount-Wim /MountDir:C:\wmount /Commit
# Auditar o que entrou:  dism /Image:C:\wmount /Get-Drivers /Format:Table

Build do driver do touch (WDK)

msbuild "E:\cel\cel\drivers\gtx9886-driver\vhidmini2.sln" /p:Configuration=Release /p:Platform=ARM64 ^
        /t:Rebuild /p:SkipPackageVerification=true /p:EnableInf2cat=false
# Saída: ...\driver\kmdf\ARM64\Release\vhidmini.sys (test-assinado)
06 — Plano

O caminho até o toque.

O alvo é único e claro: destravar o qcspmi → subir o PMIC → e com ele cai tudo (touch + USB + WiFi + botões).

  1. Visibilidade (serial). CP2102/FT232 (R$30–45) na UART \_SB.UARD @0xA88000 — com level-shift 1.8V (UART do cel é 1.8V; o conversor é 3.3V). KDCOM → kd ao vivo.
  2. Ver o hang. Bootar com o full set (DSDT 14xx) → kd mostra exatamente onde o qcspmi pendura (qual acesso SPMI trava).
  3. Init mínima do SPMI no UEFI. Fazer só aquela inicialização (sem o backend inteiro que crasha) — ou achar no Project-Aloha (fonte do moorea) como eles fazem.
  4. Subir o PMIC. Com o SPMI ok, qcspmi+qcpmic sobem → a LDO11_C pode ser votada.
  5. Acender o touch. AVDD on → IC responde → driver lê → toque. (E de quebra: Type-C/OTG, qcwlan/WiFi, botões.)
Atalho possível (sem serial)

Deployar o full set + migrar o DSDT p/ 14xx + pôr o qcspmi como demand-start (em vez de boot-start). Se o hang for só timing de boot, isso desvia. Incerto (pode só mover o hang), mas é offline e barato de testar.

Por que dá pra ter esperança

Saímos de uma "parede do PMIC" vaga para um alvo específico, nomeado e debugável: o boot-hang do qcspmi. Os drivers existem (Project-Aloha), o boot é estável, e a infra de debug/deploy offline está toda mapeada. Falta a visão (serial) e a init certa do SPMI.
